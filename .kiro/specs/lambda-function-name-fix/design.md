# Lambda Function Name Fix Bugfix Design

## Overview

The router Lambda function fails to invoke downstream Lambda functions because environment variables contain hardcoded logical function names (e.g., "BedrockOrchestrator") instead of CDK-generated physical function names (e.g., "KisanSetuMVPStack-BedrockOrchestratorF1D5335E-8c6vEjDJfHEl"). This fix updates the CDK infrastructure stack to use the `function_name` property from Lambda construct references, ensuring environment variables automatically contain the correct physical function names at deployment time.

## Glossary

- **Bug_Condition (C)**: The condition where environment variables contain hardcoded string literals instead of CDK construct references
- **Property (P)**: The desired behavior where environment variables contain actual CDK-generated physical function names
- **Preservation**: Existing Lambda invocation logic, webhook handling, and environment variable naming that must remain unchanged
- **router_lambda**: The MessageRouter Lambda function in `infrastructure_stack.py` that routes WhatsApp messages to downstream processors
- **Physical Function Name**: The actual deployed Lambda function name generated by CDK, including stack prefix and hash suffix (e.g., "KisanSetuMVPStack-BedrockOrchestratorF1D5335E-8c6vEjDJfHEl")
- **Logical Function Name**: The construct ID used in CDK code (e.g., "BedrockOrchestrator")

## Bug Details

### Bug Condition

The bug manifests when the router Lambda attempts to invoke any of the four downstream Lambda functions (BedrockOrchestrator, VoiceHandler, CreditCalculator, SatelliteAnalyzer) using environment variables. The CDK infrastructure stack sets these environment variables using hardcoded string literals instead of referencing the Lambda construct's `function_name` property, causing "Function not found" errors at runtime.

**Formal Specification:**
```
FUNCTION isBugCondition(envVarAssignment)
  INPUT: envVarAssignment of type EnvironmentVariableAssignment
  OUTPUT: boolean
  
  RETURN envVarAssignment.variableName IN [
           'BEDROCK_ORCHESTRATOR_FUNCTION',
           'VOICE_AGENT_FUNCTION', 
           'CREDIT_CALCULATOR_FUNCTION',
           'SATELLITE_ANALYZER_FUNCTION'
         ]
         AND envVarAssignment.value IS StringLiteral
         AND NOT envVarAssignment.value IS LambdaConstructReference.function_name
END FUNCTION
```

### Examples

- **BedrockOrchestrator**: Environment variable set to `"BedrockOrchestrator"` instead of `orchestrator_lambda.function_name` → Lambda invoke fails with "Function not found: BedrockOrchestrator"
- **VoiceHandler**: Environment variable set to `"VoiceHandler"` instead of `voice_lambda.function_name` → Lambda invoke fails with "Function not found: VoiceHandler"
- **CreditCalculator**: Environment variable set to `"CreditCalculator"` instead of `credit_lambda.function_name` → Lambda invoke fails with "Function not found: CreditCalculator"
- **SatelliteAnalyzer**: Environment variable set to `"SatelliteAnalyzer"` instead of `satellite_lambda.function_name` → Lambda invoke fails with "Function not found: SatelliteAnalyzer"

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Router Lambda must continue to read environment variables using the same variable names (`BEDROCK_ORCHESTRATOR_FUNCTION`, `VOICE_AGENT_FUNCTION`, `CREDIT_CALCULATOR_FUNCTION`, `SATELLITE_ANALYZER_FUNCTION`)
- Webhook verification and message parsing logic must remain unchanged
- Lambda invocation payload structure and context passing must remain unchanged
- All other environment variables in router_lambda must remain unchanged (DYNAMODB_TABLE, S3 buckets, REGION, etc.)
- CDK stack synthesis must continue to create Lambda functions with CDK-generated physical names
- The orchestrator_lambda environment variables that already use correct references (e.g., `processor_lambda.function_name`) must remain unchanged

**Scope:**
All environment variable assignments that do NOT involve the four buggy function name variables should be completely unaffected by this fix. This includes:
- Database and S3 bucket references
- Region and account configurations
- Secret names and webhook tokens
- SNS topic ARNs
- Correctly configured function references (e.g., PROCESSOR_FUNCTION_NAME, DOCUMENT_PROCESSOR_FUNCTION)

## Hypothesized Root Cause

Based on the bug description and code analysis, the root cause is:

1. **Inconsistent Environment Variable Pattern**: The infrastructure stack correctly uses `processor_lambda.function_name` for the PROCESSOR_FUNCTION_NAME variable, but uses hardcoded strings for the four downstream function variables. This suggests copy-paste error or incomplete refactoring.

2. **Lambda Creation Order**: The four buggy Lambda functions (voice_lambda, credit_lambda, satellite_lambda, orchestrator_lambda) are created AFTER router_lambda in the code, but their construct references are available at CDK synthesis time. The developer may have incorrectly assumed they needed to use string literals because the functions were defined later.

3. **Missing Reference Pattern**: The correct pattern `processor_lambda.function_name` was established but not consistently applied to all Lambda function references in environment variables.

4. **Orchestrator Has Same Issue**: The orchestrator_lambda also has one hardcoded reference (`SATELLITE_ANALYZER_FUNCTION: "SatelliteAnalyzer"`) while correctly using construct references for other functions, indicating the same inconsistency pattern.

## Correctness Properties

Property 1: Bug Condition - Environment Variables Contain Physical Function Names

_For any_ environment variable assignment where the variable name is one of the four buggy function name variables (BEDROCK_ORCHESTRATOR_FUNCTION, VOICE_AGENT_FUNCTION, CREDIT_CALCULATOR_FUNCTION, SATELLITE_ANALYZER_FUNCTION), the fixed CDK stack SHALL set the value to the corresponding Lambda construct's function_name property, resulting in the actual CDK-generated physical function name being available at runtime.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5**

Property 2: Preservation - Non-Buggy Environment Variables Unchanged

_For any_ environment variable assignment that is NOT one of the four buggy function name variables, the fixed CDK stack SHALL produce exactly the same environment variable configuration as the original stack, preserving all existing database references, S3 bucket names, region settings, and other configuration values.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5**

## Fix Implementation

### Changes Required

Assuming our root cause analysis is correct:

**File**: `kisan-setu-mvp/infrastructure_stack.py`

**Function**: `KisanSetuMVPStack.__init__`

**Specific Changes**:
1. **Update router_lambda environment variables**: Replace hardcoded string literals with Lambda construct references
   - Change `"VOICE_AGENT_FUNCTION": "VoiceHandler"` to `"VOICE_AGENT_FUNCTION": voice_lambda.function_name`
   - Change `"BEDROCK_ORCHESTRATOR_FUNCTION": "BedrockOrchestrator"` to `"BEDROCK_ORCHESTRATOR_FUNCTION": orchestrator_lambda.function_name`
   - Change `"CREDIT_CALCULATOR_FUNCTION": "CreditCalculator"` to `"CREDIT_CALCULATOR_FUNCTION": credit_lambda.function_name`
   - Change `"SATELLITE_ANALYZER_FUNCTION": "SatelliteAnalyzer"` to `"SATELLITE_ANALYZER_FUNCTION": satellite_lambda.function_name`

2. **Update orchestrator_lambda environment variable**: Fix the one hardcoded reference in orchestrator_lambda
   - Change `"SATELLITE_ANALYZER_FUNCTION": "SatelliteAnalyzer"` to `"SATELLITE_ANALYZER_FUNCTION": satellite_lambda.function_name`

3. **Verify Lambda Creation Order**: Ensure voice_lambda, credit_lambda, satellite_lambda, and orchestrator_lambda are created BEFORE router_lambda references them (they already are in the current code)

4. **No Code Changes Required**: The Lambda function code (router.py, orchestrator.py) does not need changes - it already reads environment variables correctly using `os.environ.get()`

5. **Deployment**: After CDK deployment, the environment variables will automatically contain the correct physical function names without manual intervention

## Testing Strategy

### Validation Approach

The testing strategy follows a two-phase approach: first, surface counterexamples that demonstrate the bug on unfixed infrastructure, then verify the fix works correctly and preserves existing behavior.

### Exploratory Bug Condition Checking

**Goal**: Surface counterexamples that demonstrate the bug BEFORE implementing the fix. Confirm or refute the root cause analysis. If we refute, we will need to re-hypothesize.

**Test Plan**: Inspect the deployed Lambda function's environment variables in AWS Console or using AWS CLI. Attempt to invoke the router Lambda with a test WhatsApp message payload and observe the "Function not found" error in CloudWatch Logs. Run these tests on the UNFIXED infrastructure to confirm the bug.

**Test Cases**:
1. **Environment Variable Inspection**: Check router Lambda environment variables in AWS Console (will show hardcoded strings on unfixed infrastructure)
2. **BedrockOrchestrator Invocation**: Send a text message through webhook that should trigger BedrockOrchestrator (will fail with "Function not found: BedrockOrchestrator")
3. **VoiceHandler Invocation**: Send a voice message through webhook that should trigger VoiceHandler (will fail with "Function not found: VoiceHandler")
4. **CreditCalculator Invocation**: Send a credit request through webhook that should trigger CreditCalculator (will fail with "Function not found: CreditCalculator")
5. **SatelliteAnalyzer Invocation**: Send a satellite analysis request that should trigger SatelliteAnalyzer (will fail with "Function not found: SatelliteAnalyzer")

**Expected Counterexamples**:
- Environment variables contain logical names like "BedrockOrchestrator" instead of physical names like "KisanSetuMVPStack-BedrockOrchestratorF1D5335E-8c6vEjDJfHEl"
- Lambda invocations fail with boto3 ClientError: "Function not found"
- CloudWatch Logs show the router attempting to invoke non-existent function names

### Fix Checking

**Goal**: Verify that for all inputs where the bug condition holds, the fixed infrastructure produces the expected behavior.

**Pseudocode:**
```
FOR ALL envVar WHERE isBugCondition(envVar) DO
  deployedValue := getEnvironmentVariable_fixed(envVar.name)
  ASSERT deployedValue MATCHES pattern "KisanSetuMVPStack-[ConstructId][Hash]-[RandomSuffix]"
  ASSERT lambdaFunctionExists(deployedValue)
END FOR
```

### Preservation Checking

**Goal**: Verify that for all environment variables where the bug condition does NOT hold, the fixed infrastructure produces the same configuration as the original infrastructure.

**Pseudocode:**
```
FOR ALL envVar WHERE NOT isBugCondition(envVar) DO
  ASSERT getEnvironmentVariable_original(envVar.name) = getEnvironmentVariable_fixed(envVar.name)
END FOR
```

**Testing Approach**: Property-based testing is recommended for preservation checking because:
- It generates many test cases automatically across the environment variable domain
- It catches edge cases where unintended changes might occur
- It provides strong guarantees that behavior is unchanged for all non-buggy environment variables

**Test Plan**: Capture all environment variables from UNFIXED infrastructure, then compare with FIXED infrastructure to ensure only the four buggy variables changed.

**Test Cases**:
1. **Database Configuration Preservation**: Verify DYNAMODB_TABLE remains "KisanSetuData"
2. **S3 Bucket Preservation**: Verify S3_BUCKET_RAW, S3_BUCKET_PROCESSED, S3_BUCKET_ARCHIVE remain unchanged
3. **Region Preservation**: Verify REGION environment variable remains unchanged
4. **Webhook Configuration Preservation**: Verify WEBHOOK_VERIFY_TOKEN and WHATSAPP_SECRET_NAME remain unchanged
5. **Processor Function Preservation**: Verify PROCESSOR_FUNCTION_NAME continues to use correct reference pattern
6. **SNS Topic Preservation**: Verify SNS_ALERT_TOPIC_ARN remains unchanged
